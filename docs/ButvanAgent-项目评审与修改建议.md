# ButvanAgent 项目评审与修改建议

> 评审日期：基于当前代码状态（前端约 3300 行，后端约 1800 行 Java）。
> 优先级：P0 = 影响数据安全或正确性，建议尽快处理；P1 = 影响工程质量与可维护性；P2 = 体验或治理优化。

---

## 一、总体评价

- 结构清晰：前后端分离，后端按 `server-network` / `server-agents` 分层，前端组件按 `chat/`、`model/`、`common/` 分域，职责边界符合根目录 `AGENTS.md` 的契约。
- 抽象良好：`ModelFactory`（多厂商适配）、`AgentSecurity` + `PermissionChecker`（权限体系）、`PromptBuilder`（System Prompt 模块化）都是正确方向。
- 文档意识强：`docs/` 下已有 8 篇接入教程，根目录有 DOX 工程契约，这在个人/小团队项目中非常难得。
- 当前实现覆盖的核心闭环：多模型配置与切换 + SSE 流式对话 + 会话管理 + 工具调用与耗时持久化 + 权限审批。

---

## 二、修改建议（按优先级）

### P0-1 会话持久化从 localStorage 迁移到后端

- **现状**：会话历史存于前端 `localStorage`（见 `PROJECT.md` 2.1），但后端已有 `SessionController` 与持久化能力。
- **问题**：
  - 与产品定位"本地优先、桌面端"不符：换机器、清浏览器缓存即丢失会话。
  - 桌面端（Tauri）场景下浏览器存储并不可靠。
  - 前后端两套会话逻辑并存，职责重复、口径容易不一致。
- **建议**：以 `SessionController` 为唯一数据源，前端 `services` 通过 REST 读写会话；localStorage 仅作离线兜底或直接废弃。
- **工作量**：中（前端改数据流 + 后端补查询/删除接口 + 联调）。

### P0-2 为权限与工具链路补齐自动化测试

- **现状**：前后端均未发现任何测试文件（无 `*.test.*`、`*Test.java`、`*.spec.*`）。
- **问题**：项目核心能力是"Bash 执行、文件读写 + 分级审批"，属于高风险能力；一旦权限规则解析或判定出错，可能导致误放行危险命令，而目前只能靠人工回归。
- **建议**：
  - 优先给 `PermissionChecker`、`AgentSecurity`、`ModelFactory` 补单元测试（JUnit + Mockito）。
  - 权限测试至少覆盖：规则解析、DENY/ASK/ALLOW 行为映射、路径越界（`..` 逃逸、符号链接）、模式切换。
  - 前端给 `services/api.ts` 的错误映射与类型解析补基础单测。
- **工作量**：中（后端权限链路为主）。

### P0-3 权限配置解析失败必须显式暴露，不能静默降级

- **现状**：`PermissionChecker.parseYamlRules` 中 YAML 解析失败仅 `log.error` 后返回空规则（见 `PermissionChecker.java` 第 113-115 行）。
- **问题**：用户自定义的权限规则（如"禁止 rm -rf"）若因 YAML 语法错误而全部失效，系统会静默退回默认规则——安全上属于"fail-open"，用户无感知。
- **建议**：解析失败时 fail-fast（拒绝启动或进入受限模式），并通过接口/日志向用户明确报错原因；同时增加一条"配置校验"入口供用户在界面上检查。
- **工作量**：小。

### P1-1 文档与代码现状对齐（标注 roadmap 状态）

- **现状**：`PRODUCT.md` / `PROJECT.md` 承诺了树状项目工作区、Token 用量大盘、浏览器操控、邮件通知等功能，但当前代码并未实现。
- **问题**：读者无法区分"已实现 / 规划中"，评审或协作时容易产生预期偏差。
- **建议**：在功能列表上明确标注状态（✅ 已实现 / 🚧 开发中 / 📋 规划中），并给 `docs/` 教程索引补一行"覆盖范围"说明。
- **工作量**：小。

### P1-2 拆分单文件

- **现状**：`agent-frontend/src/App.tsx`（538 行）与 `services/api.ts`（331 行）承载了过多职责。
- **问题**：随功能增长会持续膨胀，违背"一个文件只承担一个清晰职责"的契约。
- **建议**：`api.ts` 按域拆分（`sessionApi.ts` / `modelApi.ts` / `agentApi.ts`），由 `index.ts` 统一导出；`App.tsx` 中的页面编排逻辑下放到各自页面组件。
- **工作量**：小-中。

### P2-1 建立组件复用清单，防重复实现

- **现状**：`components/common/` 已有 `Card`、`Button`、`Badge`、`Select`、`Toggle` 等原子组件，方向正确。
- **建议**：新增组件前先检查 `common/` 与 `chat/`、`model/` 域内是否可复用；为常用组件补充 `Props` 类型与受控边界说明，形成组件索引，避免后续页面各自复制实现。
- **工作量**：小（维护性投入）。

### P2-2 安全与异常处理的统一审查

- **现状**：契约要求"禁止捕获异常后静默忽略"，`PermissionChecker` 已有一处 P0-3 对应的问题。
- **建议**：全局 grep 一遍 `catch` 块，确认每处都记录上下文日志或抛出可识别业务异常；检查日志与异常响应中不输出 API Key / Token / 敏感请求体。
- **工作量**：小。

### P2-3 约定式验收与验证流程

- **现状**：`AGENTS.md` 已要求"修改后至少执行格式化、类型检查、单测、构建或静态检查"，但项目缺少统一的验证脚本。
- **建议**：在根目录提供 `package.json` 或脚本化的 check 命令（前端 `tsc --noEmit` + `vite build`，后端 `mvn -q compile`），把"验证"从口头约定变成一键命令。
- **工作量**：小。

---

## 三、建议的执行顺序

1. **P0 三项**（数据安全与正确性）→ 2. **P1 两项**（可维护性）→ 3. **P2 三项**（治理与体验）。

若人力有限，建议单次迭代只做一项，并在提交说明中标注对应建议编号（如 `fix: 会话持久化迁移至后端 (P0-1)`），便于追溯。
