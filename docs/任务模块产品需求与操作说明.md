# 任务模块产品需求与操作说明

> 文档版本：v0.1（需求评审稿）
> 编写日期：2026-09-22
> 状态：产品目标与验收依据。功能正按实施计划开发；本文列出的目标行为须以实施进度与验证结果判断是否已经具备。
> 已明确需求：支持多个任务；每天 20:30 汇总花销、待办等信息；电脑使用达到指定时长后提醒，伴随声音，手动确认后循环；日报、总结等支持邮件通知。其余细节均为建议方案，待开发前确认。

## 1. 模块定位

“任务”是自动执行与通知中心。用户设置触发条件、执行内容和通知方式后，应用在满足条件时自动执行，并保留结果与通知记录。

一个任务由以下部分组成：

**任务 = 基本信息 + 触发条件 + 执行动作 + 通知配置 + 运行规则。**

例如：“每天 20:30，汇总当天支出和待办，保存日报，通过邮件发送全文，并在电脑上通知我。”

### 1.1 与现有模块的关系

| 模块 | 职责 | 与任务的关系 |
| --- | --- | --- |
| 待办 | 保存用户需要完成的事项与完成状态 | 任务读取待办生成报告；不会因发送通知而自动完成待办 |
| 财务、日常事项 | 保存支出、日程等业务记录 | 提供报告所需的数据；任务不复制一套账本 |
| 任务 | 管理自动触发、执行和通知 | 保存规则、执行结果、投递与确认记录 |
| 聊天 | 用户与 Agent 交互 | 后续可通过对话创建任务，复用同一任务服务 |
| 账户与邮箱设置 | 管理本地绑定邮箱及发信配置 | 任务复用已验证收件地址和邮件通知总开关 |

### 1.2 第一版运行边界

- 面向本地桌面端，同一设备支持创建多个任务。
- 应用运行或驻留后台时执行任务；关闭主窗口与彻底退出应用需明确区分。
- 彻底退出、关机、休眠期间不承诺准时执行；恢复后按任务规则处理错过的触发。
- 不提供云端常驻执行、跨设备同步、关机后发邮件或跨设备去重。
- 不执行用户任意输入的系统命令、脚本或未经授权的外部操作。
- 原生能力按平台验证，不把某个平台的通知行为视为所有平台共同能力。

## 2. 可以实现哪些任务

| 场景 | 用户可以配置 | 触发后得到什么 | 建议阶段 |
| --- | --- | --- | --- |
| 一次性提醒 | 日期、时间、提醒文字 | 指定时间收到提醒 | 第一阶段 |
| 每日提醒 | 每天的时间、内容 | 每天按时提醒 | 第一阶段 |
| 每周提醒 | 星期、时间、内容 | 指定星期提醒 | 第一阶段 |
| 间隔提醒 | 间隔时长、生效时段 | 运行期间按间隔提醒喝水等 | 第一阶段 |
| 每日日报 | 时间、数据栏目、通知渠道 | 保存并发送当天截至执行时的汇总 | 第二阶段 |
| 久坐提醒 | 使用时长、休息阈值、生效时段 | 到达阈值弹出待确认提醒，确认后循环 | 第二阶段 |
| 每周总结 | 周期、统计范围、栏目 | 一周支出、待办等汇总 | 第三阶段 |
| AI 总结 | 模型、总结要求 | 在准确统计基础上补充文字总结 | 第三阶段 |
| 对话创建任务 | 用自然语言描述任务 | 解析配置，展示可检查的任务草稿 | 第三阶段 |

第一版完整交付包含第一、第二阶段以及邮件通知；第三阶段单独扩展。喝水等普通间隔提醒和按电脑使用状态触发的久坐提醒采用不同计时规则。

## 3. 用户入口与页面

### 3.1 任务主页

侧边栏增加“任务”入口。顶部使用现有统一 TopBar，提供搜索、新建任务和任务设置入口。

任务列表展示：

- 标题与模板类型，例如“每日日报”“久坐提醒”。
- 触发条件摘要，例如“每天 20:30”“连续使用电脑 45 分钟”。
- 通知渠道图标，例如系统通知、邮件、提醒窗口。
- 启用、暂停、已结束状态。
- 下次执行时间；久坐任务显示当前累计时长或等待确认。
- 最近执行结果，以及需要处理的失败或权限问题。

支持按标题搜索，按启用状态、任务类型和异常状态筛选。任务管理操作包括编辑、启用、暂停、复制、预览、立即执行、查看历史和删除。

首次进入时展示空状态及“创建第一个任务”，同时提供“每日日报”“久坐提醒”“自定义提醒”模板。

### 3.2 新建与编辑页面

采用分组表单，依次填写基本信息、触发条件、执行内容、通知方式和高级规则。复杂选项按类型展开，普通提醒不显示日报数据选项。

保存前显示自然语言预览，例如：

> 每天 20:30（Asia/Shanghai），汇总当天支出和待办，保存日报并发送至已绑定邮箱，同时展示系统通知。错过后仅在当天补执行最近一次。

支持“保存并启用”和“保存为暂停”。配置不完整时可保存为暂停，但不能启用无有效通知渠道的提醒任务。

### 3.3 任务详情

展示完整配置、下一次触发、最近执行、历史列表以及待确认提醒。报告任务可查看每次保存的报告全文；历史结果不随任务配置修改而改变。

### 3.4 全局任务设置

使用现有 SettingsGroup、SettingsRow，按以下分组展示：

- 通知：权限状态、默认声音、通知预览内容。
- 免打扰：启用开关、开始/结束时间、适用渠道。
- 邮件：发信配置、绑定收件邮箱、邮件通知总开关、测试发送。
- 后台运行：关闭主窗口后的行为、退出提示；开机启动作为后续可选项。

保存成功、删除成功、测试发送结果等短暂反馈使用全局 Message；字段错误和权限缺失保留在相应配置附近。

## 4. 任务配置字段

| 配置项 | 用户操作 | 规则 |
| --- | --- | --- |
| 标题 | 输入“久坐提醒”等名称 | 必填；同名任务允许存在，以唯一 ID 区分 |
| 说明 | 输入任务用途 | 可选，不作为可执行脚本 |
| 任务模板 | 选择提醒、日报、久坐等 | 模板提供默认值；不会自动启用未选择的渠道 |
| 触发方式 | 选择一次、每日、每周、间隔、使用时长 | 按类型显示对应字段 |
| 时间与时区 | 设置执行时间与时区 | 默认创建时系统时区，保存明确时区；系统切换时区不静默修改任务 |
| 生效范围 | 选择星期和每日时段 | 默认全天；跨午夜时段需正确处理 |
| 执行内容 | 固定文字或报告栏目 | 固定提醒不调用模型 |
| 通知渠道 | 多选系统通知、窗口、邮件 | 声音作为桌面提醒附加选项，避免重复播放 |
| 需要确认 | 选择是否人工确认 | 启用时必须使用应用提醒窗口；邮件不能承担确认 |
| 错过策略 | 跳过或有界补执行 | 按任务类型提供可选范围 |
| 启用状态 | 启用或暂停 | 暂停保留配置和历史 |

不向普通用户暴露 Cron 表达式；使用直观的时间选择器。高级 Cron 编辑不在本期范围。

## 5. 操作示例：每天 20:30 发送日报

### 5.1 创建流程

1. 打开“任务”，点击“新建任务”。
2. 选择“每日日报”模板。
3. 输入标题“每日日报”，设置每天 20:30，并检查时区。
4. 选择报告栏目，默认勾选支出和待办，可选日程、学习记录。
5. 选择通知方式，例如“系统通知 + 邮件”。
6. 邮件未配置时，通过表单中的设置入口完成发信配置与收件邮箱绑定，再返回任务。
7. 点击“预览报告”，检查当前数据生成的示例；预览不会发送真实通知。
8. 检查执行规则，点击“保存并启用”。
9. 列表显示下次执行日期、时间及通知渠道。

### 5.2 日报包含什么

| 栏目 | 展示内容 | 统计约束 |
| --- | --- | --- |
| 基本信息 | 报告日期、统计起止时间、实际生成时间 | 20:30 日报标注“截至 20:30”，不称为全天最终结算 |
| 支出 | 支出总额、分类汇总、可选明细 | 明确唯一权威数据源；同一笔支出不能从财务和日常事项重复计入；不同币种不直接相加 |
| 待办 | 当日应办事项、完成数、未完成列表 | 按日历现有周期投影规则归属日期；完成状态为报告快照时状态 |
| 日程 | 当日日程标题、时间 | 仅统计用户选择的范围 |
| 学习 | 学习记录、已记录时长 | 缺失时长不推测补齐 |
| 总结 | 固定格式摘要，后续可选 AI 文字总结 | 金额与数量由业务统计提供，不让模型自行计算或编造 |

本期不承诺“今天实际完成了多少历史待办”的历史行为统计；若现有数据缺少完成时间，需要先补齐记录能力。报告栏目读取失败时标注“数据暂不可用”，不能显示为 0。全部栏目失败时，本次生成失败。

### 5.3 报告示例

以下为虚构示例，不代表用户真实数据：

```text
每日日报 · 2026-09-22
统计范围：2026-09-22 00:00 至 20:30（Asia/Shanghai）

今日支出：¥86.00
餐饮 ¥56.00；交通 ¥30.00

今日应办：5 项
截至统计时已完成 3 项，未完成 2 项
未完成：整理会议记录、阅读技术文章

学习记录：1 条，共 40 分钟
```

### 5.4 到点后的行为

应用创建一次执行记录，读取所选数据并保存报告快照，然后独立投递各通知渠道。邮件发送报告全文，系统通知显示简短摘要，点击通知进入对应报告详情；平台不支持点击路由时提供应用内详情入口。

如果邮件失败，已保存报告仍可查看，系统通知也不受影响；重试邮件使用原报告，不重新读取数据或生成另一份日报。

## 6. 操作示例：每使用电脑 45 分钟提醒休息

### 6.1 创建流程

1. 新建任务，选择“久坐提醒”。
2. 输入标题、提醒文案，设置使用时长为 45 分钟。
3. 设置连续空闲达到 5 分钟视为一次休息；该值为建议默认值，可修改。
4. 可限定周一至周五、09:00—18:00 生效。
5. 勾选系统通知、提醒声音和“需要手动确认”。
6. 使用“预览提醒”查看示例窗口；只有点击“测试通知”才产生真实测试通知。
7. 保存并启用，任务详情显示当前计时状态。

### 6.2 使用时长的建议定义

本期建议采用“系统未锁定、未休眠，且空闲时间未达到休息阈值”的连续使用估算，不读取屏幕内容，不记录按键内容，也不判断身体姿态。

- 从启用或确认后开始计时；短于休息阈值的无操作间隔仍算连续使用。
- 连续空闲达到休息阈值后，清零并进入等待使用状态；恢复活动后重新开始。
- 锁屏、休眠期间不累计；达到休息阈值则清零，较短中断保留之前计时。
- 超出生效时段停止计时并清零，下一个生效时段重新开始。
- 应用彻底退出后无法采集；再次启动重新计时，不把退出期间当作使用时间。
- 长时间阅读、观看视频可能被识别为空闲。这是该口径的已知限制；屏幕亮起时长模式作为后续选项，不默认声称能够识别这些活动。

使用时长口径尚待用户确认。平台无法提供可靠检测时，显示“不支持使用状态检测”；不能静默改成普通 45 分钟倒计时。

### 6.3 达到阈值后的行为

1. 创建一条待确认提醒，桌面显示系统通知与应用独立提醒窗口。
2. 窗口展示标题、提醒文案、触发时间及“确认并重新计时”按钮。
3. 建议默认只播放一次声音；可选按配置间隔重复播放，避免系统和应用同时播放两遍。
4. 未确认期间停止当前轮次计时，不生成同一任务的新提醒。
5. 点击确认后，保存确认时间，关闭窗口和声音，从 0 开始下一轮。

这里的确认表示“用户已处理提醒”，不证明用户已经休息。系统通知被划走或清除不等于确认。应用提醒窗口不自动消失；窗口关闭操作不能隐式标记为确认，可引导用户确认或暂停任务。

允许用户从任务页暂停：暂停后停止声音与后续触发，当前提醒记录为“因暂停撤回”，不是“已确认”。彻底退出应用仍应允许，未确认状态保留，重启后在允许提醒的时段恢复。若需要“稍后提醒”，作为后续独立功能，不混入确认语义。

### 6.4 多个提醒同时发生

同一任务最多保留一条待确认提醒。不同任务同时触发时使用统一提醒窗口展示待处理列表，逐项确认，避免弹出大量窗口；单项确认只影响该任务。

## 7. 通知渠道与声音

| 方式 | 适用内容 | 用户操作 | 边界 |
| --- | --- | --- | --- |
| 系统通知 | 简短提醒、报告完成提示 | 查看或进入应用详情 | 受系统通知权限、专注模式、显示样式影响 |
| 应用提醒窗口 | 必须手动确认的提醒 | 点击确认；或在任务页暂停 | 应用运行时维持待确认状态，不承诺覆盖锁屏或所有全屏应用 |
| 声音 | 桌面提醒的辅助提示 | 选择开关、试听、重复模式 | 受系统音量等影响；不能保证静音状态下可听见 |
| 邮件 | 日报、周报、较长总结 | 打开邮件阅读全文 | 网络与邮件服务可用时发送，不等同于阅读或确认 |

需要手动确认时，由应用持久化确认状态，不能仅依赖系统通知是否留在屏幕上。macOS 的持续通知样式由系统设置控制，其他平台需要分别验证。

系统通知可默认只显示“日报已生成”，用户选择后才在通知预览中展示金额或待办内容。完整报告始终可在应用内查看。

## 8. 邮件通知的配置与使用

### 8.1 复用已有邮箱能力

项目已有本地邮箱绑定、验证邮件发送及 `config.json` 的 `mail` 配置约定，详见[本地邮箱绑定方案](邮箱绑定方案.md)。任务模块应复用，不另建用户账户或独立保存一份 SMTP 密钥。

发件邮箱是发送服务使用的地址，收件邮箱是用户接收报告的地址，两者可以不同。第一版建议只发送到当前已验证的绑定邮箱；多个收件人、抄送和任意自定义收件地址后续扩展。

### 8.2 首次设置流程

1. 打开“设置 → 任务 → 邮件通知”。
2. 输入 SMTP 服务器、端口、加密方式、用户名、认证凭据和发件地址。
3. 保存发信配置，凭据输入框不回显已保存明文；留空表示保持原凭据。
4. 通过现有邮箱绑定流程验证收件地址；未绑定时不得直接发送业务报告。
5. 开启邮件通知总开关。
6. 点击“发送测试邮件”，向已绑定邮箱发送无业务数据的测试内容。
7. 在具体任务中勾选邮件通知，保存并启用。

具体加密方式需与既有 SMTP 适配器能力统一，不能仅在界面新增选项而底层不支持。保存配置不自动发送测试邮件。

### 8.3 邮件内容

- 默认主题：“每日日报 · 日期”，可使用受限的任务名、日期变量。
- 正文提供排版后的 HTML 与纯文本备用内容，展示统计范围、各栏目、实际生成时间。
- 邮件中的正文来自已保存报告；用户输入和模型输出必须安全转义。
- 不依赖仅本机有效的链接才能阅读报告，不默认添加追踪像素或已读追踪。
- 附件、PDF 导出和回复邮件操作不在第一版范围。

### 8.4 邮件通知开关与地址变更

只有“全局邮件开关开启 + 任务选择邮件 + 当前邮箱已验证 + 发信配置有效”同时满足时才发送。关闭全局开关阻止尚未开始发送的邮件和自动重试，保留报告及记录；已经提交给邮件服务的邮件无法撤回。

待发送记录绑定生成时的已验证收件地址。邮箱重新绑定后，旧地址的未发送记录停止投递并提示用户处理，不能悄悄改发到新地址；后续新执行使用新绑定地址。发送前重新检查权限与开关。

### 8.5 发送状态与重试

| 状态 | 对用户的含义 | 后续操作 |
| --- | --- | --- |
| 待发送 | 已生成内容，等待投递 | 可查看排队原因 |
| 已提交邮件服务 | SMTP 服务确认接收 | 不代表到达收件箱或已阅读 |
| 发送失败 | 明确未成功提交 | 查看原因，按分类重试 |
| 发送结果未知 | 连接中断等导致无法判断服务是否接收 | 提醒可能已发送，默认不自动重发 |
| 已跳过 | 用户关闭渠道、过期或任务被删除等 | 显示原因 |

建议对可明确安全重试的临时失败，在 1、5、15 分钟后各重试一次；认证错误、地址错误等配置问题不自动反复重试。用户手动重发需明确提示可能重复，并记录为新的投递尝试。

以执行 ID、渠道和收件地址建立投递唯一约束，避免重复调度；SMTP 无法保证端到端恰好一次投递，不能承诺网络异常时绝不重复。固定 Message-ID 只能辅助追踪，不能当作收件服务去重保证。

## 9. 任务日常操作

| 操作 | 具体行为 |
| --- | --- |
| 编辑 | 保存新配置；尚未开始的触发按新配置计算；已生成结果保留原配置快照 |
| 暂停 | 阻止新触发与未开始投递，撤回桌面待确认提示并记录原因；正在进行的不可撤回投递如实记录结果 |
| 恢复 | 从当前时间重新计算下次触发；不补发暂停期间的历史任务 |
| 复制 | 创建新的暂停任务，复制配置但不复制执行历史 |
| 预览 | 展示示例报告或窗口，不发送、不改变计时、不算一次正式执行 |
| 立即执行 | 明确提示将使用所选渠道真实通知；创建手动执行记录，不替代下一次计划执行 |
| 重试渠道 | 只重试失败或可处理的渠道，复用原结果 |
| 删除 | 确认后停止任务并取消尚未开始的投递；保留带原名称的历史记录供查看 |
| 清理历史 | 单独确认删除选定历史；不影响任务配置，不撤回已发送邮件 |

同一任务已有执行正在进行时，不再并行启动新执行，记录本次触发被跳过的原因。对于久坐任务，立即执行将产生真实待确认提醒并停止当前计时；已在等待确认时不重复创建。

## 10. 调度、免打扰与恢复规则

### 10.1 时间规则

- 每日、每周任务按保存的时区和当地时间计算。
- 间隔任务按应用运行期间的经过时长计算，不把关机时间积累为多条待发提醒。
- 系统时间后调不能重复执行同一计划实例；前调按错过策略处理。
- 夏令时不存在的本地时间建议当天跳过；重复出现的本地时间只执行一次。界面应能预览下次执行结果。
- 日报使用计划日期确定归属，实际执行时刻作为数据截止时间。补执行不能伪装为原计划时刻的数据快照。

### 10.2 错过触发

| 类型 | 建议默认行为 |
| --- | --- |
| 每日日报 | 当天恢复时只补最近一次，标注补执行和实际截止时间；跨天不自动补发 |
| 一次性提醒 | 过期后显示已错过，允许用户手动执行 |
| 每日/每周普通提醒 | 跳过错过的实例，等待下一次 |
| 间隔提醒 | 从恢复时重新计算间隔，不连续补发 |
| 久坐提醒 | 新计时不补偿离线时长；既有待确认提醒按规则恢复 |

### 10.3 免打扰

建议默认仅约束桌面通知、提醒窗口和声音，邮件是否受限单独配置。免打扰不停止报告生成。

- 免打扰期间新产生的普通桌面通知可跳过并记录，不在结束时集中轰炸。
- 需要确认的提醒保留待确认记录，在免打扰结束后统一展示；期间不再创建同任务新提醒。
- 开始免打扰时隐藏现有窗口并停止声音，不自动确认；结束后恢复待确认列表。
- 若用户选择邮件也受免打扰限制，则排队至结束后投递；建议超过 24 小时的排队邮件跳过并保留报告。
- 应用免打扰与操作系统专注模式分别生效，不能声称绕过系统限制。

### 10.4 重启与断线

任务规则、执行结果、投递状态、待确认记录必须持久化。重连时先恢复后端权威快照，再接收事件增量，不凭前端内存推断任务完成。

崩溃恢复时区分“尚未生成”“已生成未发送”“投递结果未知”和“等待确认”。不能简单把所有未结束执行重新跑一遍。已保存结果直接复用；没有完整结果的中断执行保留中断记录，再按错过策略判断是否新建恢复执行。

## 11. 异常情况下用户会看到什么

| 情况 | 展示与处理 |
| --- | --- |
| 系统通知未授权 | 显示权限提示与设置入口；其他已启用渠道仍可工作 |
| 使用状态检测不可用 | 久坐任务显示受阻原因，不伪造计时 |
| 发信配置缺失 | 邮件选项提示完成配置；可先保存暂停任务或选其他渠道 |
| SMTP 认证失败 | 报告保留，邮件显示失败与修复入口，不反复自动尝试 |
| 网络中断 | 明确未提交的投递有限重试；不确定是否提交则显示结果未知 |
| 某个报告栏目读取失败 | 报告标记内容不完整，展示缺失栏目；可投递带提示的报告 |
| 所有报告栏目读取失败 | 执行失败，不发送一份假装为空的日报 |
| AI 模型失败 | 使用已生成的基础报告，标注未生成 AI 总结 |
| 所选栏目没有数据 | 正常生成“无记录”的报告，区别于读取失败 |
| 主窗口关闭 | 若启用后台驻留，继续运行；界面和托盘明确显示后台状态 |
| 应用彻底退出 | 停止调度，退出前提示任务不会继续运行 |

## 12. 状态和记录设计

任务配置状态、执行状态、通知状态、确认状态分别记录，避免“邮件失败”把任务变成永久停用。

| 对象 | 建议状态 |
| --- | --- |
| 任务 | 启用、暂停、已结束、已删除 |
| 执行 | 等待、执行中、成功、部分成功、失败、跳过、中断 |
| 渠道投递 | 待投递、投递中、已提交、失败、结果未知、跳过 |
| 提醒确认 | 待确认、已确认、已撤回 |

执行记录包含唯一 ID、任务 ID、配置版本、计划时间、实际时间、执行来源、统计范围、结果快照和错误摘要。投递记录包含渠道、脱敏目标、尝试次数、最近结果；确认记录包含触发、确认或撤回时间。

任务详情分别显示“内容已生成”“邮件已提交”“提醒待确认”。只有用户确认接口成功保存后，才能将待确认提醒更新为已确认；重复点击确认应幂等处理。

## 13. 技术落点与项目约束

本节描述建议职责，不是已经存在的接口或最终数据库设计。实现前需继续读取目标目录适用的 AGENTS.md，并细化 DTO、接口错误语义和权限边界。

| 位置 | 建议职责 |
| --- | --- |
| `agent-frontend/src/components/task/` | 任务列表、编辑、详情、报告与提醒视图 |
| `agent-frontend/src/services/` | 任务 HTTP、SSE 与桌面能力适配；不在组件直接请求 |
| `agent-frontend/src/types/` | 任务、执行、通知等前端 DTO |
| `agent-frontend/src-tauri/` | 使用状态采集、锁屏/休眠适配、通知、声音与后台驻留 |
| `agent-backend/server-network/task/` 对应 Java 业务包 | 配置、调度、执行、报告聚合、投递及 SQLite 持久化 |
| `agent-backend/server-network/` 既有邮件能力 | 复用并扩展发信配置与投递适配，不将验证码发送逻辑直接当作报告模板 |
| `agent-backend/server-agents/` | 后续提供有界的模型总结能力；不反向依赖 network 业务实现 |

后端负责权威调度与状态；Rust 提供桌面采集和显示，页面关闭不能中断计时服务。桌面投递通过带 ID 的通知命令和回执关联，前端不得自己重复调度。任务 SSE 在事务提交后发布事件，建立连接和重连时先返回快照。

任务、执行和通知记录保存到现有本地 SQLite 领域表；邮件配置继续使用现有 `~/.butvan-agent/config.json` 约定。凭据不进入任务表、日志、报告、接口响应或仓库，配置文件应限制为当前用户访问；操作系统凭据库迁移可另行规划。

AI 总结是可选步骤，输入仅为用户选择的报告数据，设置 Token 预算；非聊天模型用量沿用系统用量记录规范。不得为日报自动加载整个工作区、历史对话或个人记忆。

新增任务工具时应接入 ToolSchemaRoutingPolicy 能力分组。自然语言创建不能直接把自由文本作为可执行指令，必须转换成允许的结构化配置。

### 13.1 DOX 复核

本次仅新增规划文档，没有改变实际接口、权限、持久化位置、目录职责或产品行为，因此不修改根 AGENTS.md 的现行工程契约。落地上述能力时，需同步维护任务职责、邮件权限、原生检测与后台生命周期等适用规范及索引；文档中的拟议规则不能自动视为已经生效的工程规范。

## 14. 分阶段交付与验收

### 14.1 第一阶段：任务与通知基础

交付任务管理、一次/每日/每周/间隔触发、系统通知、执行历史、后台运行、邮件配置与发送、恢复与去重基础。

验收：创建后能预览下次执行；暂停后不再触发；主窗口关闭但后台驻留时仍能运行；邮件失败不阻断桌面通知；重启不重复提交已知成功的投递；预览不产生外部通知。

### 14.2 第二阶段：日报与久坐提醒

交付日报数据聚合、历史报告、邮件全文、使用状态检测、提醒窗口、人工确认与循环。

验收场景：

1. 每天 20:30 保存一份带统计截止时间的日报，并按选定渠道投递。
2. 支出无记录显示 0，读取失败显示不可用，不混淆两者。
3. 邮件重试沿用同一报告，不能生成第二份不同内容的日报。
4. 测试时使用可控时钟模拟 45 分钟，到阈值只产生一条待确认提醒。
5. 清除系统通知不确认任务；手动确认后重新计时。
6. 持续空闲、锁屏、休眠、超出生效时段均按已选规则处理。
7. 待确认时重启，恢复同一提醒；暂停后声音停止且记录为撤回。
8. 两个任务同时触发时可分别处理，无重复弹窗或串改状态。
9. SMTP 超时且结果不确定时显示结果未知，不盲目重发。
10. 时钟跳变、时区和夏令时测试覆盖重复或错过触发。
11. 多窗口及断线重连后与后端状态一致。
12. 各目标操作系统分别验证原生检测、权限、声音和后台运行；未验证的平台不宣称完整支持。

以单元测试、集成测试、类型检查、构建和可控时钟验证为主。原生能力的实际系统验收需另行安排；未获得用户要求时，不自行开展截图或逐页手动界面检查。

### 14.3 第三阶段：扩展

- 每周、每月总结和更多报告栏目。
- 可选 AI 分析、总结风格与模型选择。
- 聊天创建、修改、暂停任务，保存前展示结构化配置。
- 稍后提醒、自定义声音、多收件人、附件导出。
- 开机启动及更多通知渠道；云端执行属于独立架构范围。

## 15. 开发前需要确认的产品决策

| 决策 | 建议默认方案 | 影响 |
| --- | --- | --- |
| 平台顺序 | 优先验证 macOS，再按产品要求覆盖 Windows/Linux | 原生检测与通知实现成本 |
| 久坐计时口径 | 系统空闲阈值估算连续使用，默认 5 分钟视为休息 | 阅读、视频等无操作场景是否计时 |
| 强提醒形式 | 系统通知配合应用提醒窗口 | 满足手动确认要求的方式 |
| 声音 | 默认一次，可开启重复播放 | 打扰程度与免打扰行为 |
| 后台行为 | 可配置关闭主窗口后驻留；彻底退出停止执行 | 用户对运行状态的理解 |
| 邮件收件人 | 第一版仅当前已验证邮箱 | 是否需要多地址验证与权限管理 |
| 日报生成 | 第一版固定模板，AI 后续可选 | 模型成本与结果稳定性 |
| 首版边界 | 完成第一、第二阶段，邮件包含在内 | 排期与验收范围 |

上述建议仍待产品确认；本次文档编写不创建真实任务、不发送邮件、不修改系统通知权限，也不启动功能开发。
